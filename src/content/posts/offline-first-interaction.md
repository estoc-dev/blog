說一個 app「離線優先」，通常是指它沒有網絡也能打開、能編輯，連上了再同步。我們想把這個要求推到人與人之間：證明我是誰、簽一份合約、讓另一把鑰匙代我登入、交換名片，這些事在沒有網絡的時候也要成立。網絡只負責把東西搬過去，搬得慢、搬丟了、搬了兩次，都不改變事情本身。

從這個角度出發，下面是目前定下來的幾塊。有的已經寫成程式碼，有的還是計劃。

## 身份：一個接口，三種實現

從別人的角度看，一個身份就是一個能簽名的東西。所以我們不先規定它是哪種鑰匙，只規定它要做到的兩件事：

```ts
interface Signer {
  readonly identity: Identity
  sign(digest: Uint8Array): Promise<Uint8Array>
}

function verify(identity: Identity, digest: Uint8Array, signature: Uint8Array): boolean
```

- `sign` 在持有者那邊，替一份物件的 hash 簽名。它是非同步的，因為簽名的可能是記憶體裏的一把鑰匙，也可能是一個要人按一下才簽的錢包。
- `verify` 在任何人那邊：有身份、hash 和簽名就能驗，不連網，也不問任何伺服器。

實現得了這兩件事的，都可以是身份。第一版支援三種：普通的 Ed25519 鑰匙、以太坊錢包的 `personal_sign`，以及 Solana 的 off-chain message。三者把要簽的內容包成不同的格式，但都能替一段文字簽名，也都能只憑公鑰在本地驗。合約錢包做不到後一半：它的簽名要上鏈查詢才驗得了，所以接不進來。

包裝的格式屬於身份，不屬於簽名：放在錢包裏的鑰匙只會用那個錢包的格式簽，驗的人也就不必接受持有者沒選過的格式。所以一個身份是一把公鑰加上它的簽名方式，同一把鑰匙換一種格式，就是另一個身份。寫進物件裏時，身份就是這兩樣：

```json
{"publicKey": "<hex>", "scheme": "ed25519"}
```

身份只簽一樣東西：一份物件的 hash，簽的文字是 `Estoc Object (sha256:<hex>)`。用文字，是因為錢包會把它顯示給持有者看。登入、授權，也都寫成物件再簽，所以一份簽名冒充不了另一種用途的簽名。

## 物件：從哪條路收到都是同一份

傳來傳去的東西，都是一份物件：一個 JSON 值，加上它所遵守的 JSON Schema 的連結。

```
Object  {"data": <任何 JSON 值>, "schema": "sha256:<schema 的連結>"}
```

- 編碼用 JCS（[RFC 8785](https://www.rfc-editor.org/rfc/rfc8785)）：一個值只有一種 bytes，也就只有一個連結，連結是 `sha256:` 加上這些 bytes 的 SHA-256。同一份物件，不管是直接收到、經別人轉寄，還是從備份裏找回來，連結都一樣，可以拿連結去重、引用、核對。
- 解碼是嚴格的，多一個空格、key 的順序不對，都讀不進來，所以一個連結不會對應兩種寫法。
- schema 本身也是 JSON，用同一套編碼，也有自己的連結。讀物件時，讀者給出自己預期的 schema，寫給別的 schema 的物件就讀不進來，應用不會把別人的資料錯當成自己的。
- 一個值合不合 schema，由驗證器判斷。驗證器是插件，只要守三條：不連網、同樣的輸入給同樣的結論、`$ref` 解不開時在編譯階段就拒絕。

## 簽名：收到的順序不要緊

```
Signature  {"identity": <身份>, "object": "sha256:<物件的連結>", "signature": "<hex>"}
```

一份簽名只說：這個身份站在這份物件後面。它不帶角色，也不帶時間。誰要簽、簽齊了沒有、什麼時候生效，都由讀這份物件的應用，按它的 schema 決定。

每份簽名是獨立的一個 blob，各自傳送。一份買賣合約，買方和賣方各簽一份、各自寄出，哪份先到、到了幾次都不要緊：登記處把收到的全部讀一遍，雙方的簽名都在，合約就成立。少了一份，就等它到；它到了，結論從「還沒成立」變成「成立」，不會反過來。

驗一份簽名只需要簽名本身，因為它簽的 hash 就寫在連結裏。

## 授權與代理：沒有撤銷，只有到期

硬體錢包不適合每次登入都拿出來按一下。所以一個身份可以授權另一個身份代它行事，例如讓瀏覽器裏的一把鑰匙代錢包登入。

```
Authorization  {"agent": <身份>, "until"?: <時間>}                由授權者簽
Proxy          {"target": <物件的連結>, "chain": [<授權簽名的連結>, …]}  由最後一個代理人簽
```

- 誰簽了 Authorization，誰就是授權者，物件本身不寫。授權是全權的，包括再授權別人。
- 代理人不直接簽目標物件，而是簽一份 Proxy，寫明經過哪一條授權鏈、替誰簽。不然代理人以自己名義簽的東西，例如作為見證人的簽名，會被當成授權者的。
- 授權靠 `until` 結束，沒有撤銷。離線時，撤銷的通知未必及時送到；而且如果多收到一個 blob 就能推翻一次授權，任何讀出來的結論都定不下來。想收得回來，就給短一點的 `until`，到期前再續。`until` 用讀者自己的鐘來判斷。

讀者拿一份簽名當入口，順著連結逐個取出它牽到的 blob、核對內容，讀出「錢包站在這次登入後面，經過瀏覽器裏的這把鑰匙」。

## 信箱：網絡是加上去的一層

到這裏都不需要網絡。要把東西送到別人手上，才需要聯絡的方式。我們把它從身份裏拆出來，叫信箱：

```
Mailbox  {"key": <x25519 公鑰>, "until"?: <時間>, <傳輸自己的欄位>…}
```

- 一個信箱說的是：封給這把鑰匙、經這個傳輸送到這裏的信，會到持有鑰匙的人手上。它不寫屬於誰。一個身份簽了某個信箱，那就是一張名片；一次性的邀請，可以發一個沒人簽的信箱。
- 傳輸是插件：直連、HTTP、relay，各自定自己的那份 schema。拿到信箱的人只管寄，不碰鑰匙、加密和傳輸。
- 信都用 HPKE（[RFC 9180](https://www.rfc-editor.org/rfc/rfc9180)）的 base mode 封給收件人的鑰匙。封好的 bytes 不說是誰封的；傳輸看得到誰把信交給它，看不到內容。
- 簽名也不說是誰寄的，轉寄別人簽過的東西是正常的用法。需要知道一封信寫給誰的應用，例如聊天，把收件人寫進自己簽的物件裏。
- 不確認送達，也不重寄：信可能丟失、重複、亂序。前面幾塊讓這不成問題：blob 按內容命名，重複的只是同一份；結論只隨收到的東西增加，晚到的照樣算。

## Bundle：見面時交換一個文件

將來見面交換名片，多半是交換一個文件，經 NFC 或 AirDrop，不必經過任何伺服器。後量子簽名的公鑰本來就放不進 QR code，所以不必為了 QR 省 bytes。一張名片要帶身份、信箱、簽名、名字和頭像，經代理的還要帶授權鏈，這就需要把一批 blob 打成一包。

```
index.json          root：一份物件的 JCS bytes
blobs/sha256/<hex>  其他 blob，檔名就是內容的 SHA-256
```

- 一包一定以一份物件為入口，讀者看 root 的 schema，就知道這包是什麼。
- 檔名就是 hash，照 [OCI image layout](https://github.com/opencontainers/image-spec/blob/main/image-layout.md) 的寫法，路徑不帶別的意思。內容和檔名對不上，整包拒絕。
- 收下 bundle 是信任的邊界：在這裏驗一次連結和簽名，之後不再驗。`until`、誰站在後面、合不合 schema，跟讀者和時鐘有關，讀的時候再算。
- 要當一個檔案搬的時候壓成 zip。zip 只是外殼，任何工具壓的都行。

## 貫穿這幾塊的

- 驗證只看手上的 bytes，不問伺服器。
- 結論只隨收到的東西增加，所以不怕丟失、重複和亂序。
- 和時間有關的判斷，用讀者自己的鐘。
- 傳輸可以換，換了不影響其他幾塊。

## 還沒定的

- 存放：收進來的 bundle 怎麼存、怎麼建索引，例如一份物件有哪些簽名、一個身份簽過什麼。我們想記下每個 blob 收進來的時間，將來某種簽名方式被攻破時，攻破之前收到的仍然可信。
- 群組與多人的頻道。
